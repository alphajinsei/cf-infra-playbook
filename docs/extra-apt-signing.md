# 番外編：apt の署名鍵と GPG

最終更新：2026-11-02

[学習ロードマップ](learning-roadmap.md) の Step 0-2 で、gh と Terraform を入れたときにやったことの整理。

## やったこと

どちらも同じ流れ。

1. 配布元の署名鍵（公開鍵）をダウンロードして手元に置く
2. 配布元（apt リポジトリ）の URL を apt に登録し、「この配布元はあの鍵で検証する」と指定する
3. `apt update` → `apt install`

Ubuntu 標準の apt には入っていないか古いので、配布元を追加する。以後は `sudo apt upgrade` で一緒に更新される。

## 署名鍵とは

配布元の公開鍵。サーバ証明書と目的は似ている（相手が本物かを確かめる）が、確かめる対象が違う。

| | 確かめる対象 | 誰が保証するか |
| --- | --- | --- |
| サーバ証明書（TLS） | いま通信しているサーバが本物か | 認証局（CA） |
| 署名鍵（GPG） | 受け取った中身（パッケージ）を本物の配布元が作ったか | 第三者はいない。自分で「この鍵を信じる」と決めて置く |

中身を確かめる仕組みなので、途中のミラーサーバーやキャッシュがすり替えられても検知できる。

## SSH の known_hosts / authorized_keys との比較

「信頼する相手の公開鍵を、あらかじめ手元に置いておく」という点で同じ考え方。

| | 誰が誰の公開鍵を置くか | 何を確かめるか |
| --- | --- | --- |
| `~/.ssh/known_hosts` | クライアントがサーバの公開鍵を置く | 接続先のサーバが本物か |
| `~/.ssh/authorized_keys` | サーバがクライアント（ユーザー）の公開鍵を置く | ログインしてきた人が本人か |
| apt の署名鍵 | 自分（受け取る側）が配布元の公開鍵を置く | パッケージを本物の配布元が作ったか |

向きでいうと apt の署名鍵は known_hosts に近い（受け取る側が、送ってくる側の鍵を置く）。違いは、SSH は「接続の相手」を確かめ、apt は「ファイルの中身」を確かめること。apt の鍵は、配布元が秘密鍵で署名したファイルなら、どこから受け取っても検証できる。

## GPG とは

GPG（GNU Privacy Guard）は、OpenPGP という署名・暗号の規格を実装したツール。鍵の形式の名前としても使われる。

## 検証の仕組み

1. 配布元は、パッケージ一覧の目次（`Release` ファイル）を秘密鍵で署名して公開している。目次には各パッケージ一覧のハッシュ値が載っている。
2. `apt update` で目次を取ってくると、手元の公開鍵（署名鍵）で署名を検証する。
3. 目次のハッシュ値でパッケージ一覧を確かめ、一覧に載っているハッシュ値で各 `.deb` ファイルを確かめる。

署名を1つ確かめれば、ハッシュ値の連鎖で全パッケージが本物だと分かる。

yum / dnf で「GPG 鍵がなくてインストールに失敗する」のは、2 の時点で検証に使う公開鍵が手元にないから。配布元が鍵を更新したときにもよく起きる。なお rpm はパッケージ1つ1つにも署名がある。

## 手元への登録の仕方

置き場所は2か所に分かれる。

| ファイル | 中身 |
| --- | --- |
| `/etc/apt/keyrings/githubcli-archive-keyring.gpg`（Terraform は `/usr/share/keyrings/hashicorp-archive-keyring.gpg`） | 鍵そのもの |
| `/etc/apt/sources.list.d/github-cli.list`（Terraform は `hashicorp.list`） | 配布元の URL と、検証に使う鍵の指定 |

実際の `.list` の中身：

```
deb [arch=amd64 signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main
```

`signed-by=` で、この鍵をこの配布元にしか使わないように結び付けている。昔は `apt-key add` で鍵を全体に登録する方式だったが、ある配布元の鍵で別の配布元のパッケージを偽装できてしまうので廃止された。

Terraform の手順にあった `gpg --dearmor` は、テキスト形式の鍵（`-----BEGIN PGP PUBLIC KEY BLOCK-----` で始まるもの）を、apt が読むバイナリ形式に変換している。gh の鍵は最初からバイナリ形式なので、そのままコピーしている。

## 信頼の出発点

最初の鍵は HTTPS でダウンロードしているので、その時点ではサーバ証明書（TLS）に頼っている。一度置いた鍵は、以後どこから受け取ったパッケージにも使える。SSH の known_hosts で最初の接続時に「この鍵を信じますか？」と聞かれるのと同じで、最初の1回をどう信じるかが出発点になる。
