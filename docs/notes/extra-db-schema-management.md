# 番外編：DB のスキーマ管理（素の DDL → マイグレーション → Drizzle）

最終更新：2026-11-03

[学習ロードマップ](../roadmaps/cloudflare.md) の Step 4〜5 で出てきた、DB の構造（テーブルや列）をどう管理するかの整理。

## 3つの段階

| | 素の管理 | マイグレーション | Drizzle |
| --- | --- | --- | --- |
| 書くもの | その場で流す DDL | 変更の手順（CREATE、ALTER…）を番号付きのファイルで | あるべき最終形（`schema.ts`） |
| 適用の記録 | なし | DB の中の表（D1 なら `d1_migrations`） | マイグレーションと同じ（Drizzle は SQL を作るだけで、流すのは wrangler） |
| あるべき姿がどこに見えるか | どこにもない | ファイルを頭から全部たどれば分かる | `schema.ts` を見れば分かる |
| 変更の書き方 | 手で DDL を書く | 手で ALTER などを書く | `schema.ts` を直すと、差分の SQL が自動で作られる |
| アプリのコードとの関係 | 別々に管理 | 別々に管理（型や SQL の文字列を手で合わせる） | 同じ定義からアプリの型も作られる |
| インフラでたとえると | サーバーに ssh して手で設定 | 番号付きの手順書（1回ずつ流し、どこまで流したか記録する） | Terraform に近い（あるべき姿 → 差分）。ただし差分の比較相手は実物ではなくスナップショット |

## 1. 素の管理

DDL の `.sql` を、必要になったら各環境に手で流す。

困ること：

- どの環境に何を流したかの記録がない。開発・検証・本番で構造がずれていく。
- 本番にどんなオブジェクトがあるべきかが、どこにも書かれていない。
- 新しい環境を作るとき、何をどの順で流せば同じになるか分からない。

## 2. マイグレーション（wrangler、Flyway など）

変更の手順を番号付きのファイルにして git で管理し、DB の中の表に「どこまで流したか」を記録する。まだ流していない番号だけを順に流す。

解決したこと：

- 各環境が、どこまで適用済みかを自分で知っている。`migrations list` で未適用のものが分かる。
- 新しい環境は、全ファイルを頭から流せば同じ構造になる（再現性）。
- 変更がファイルになるので、git の履歴とレビューに乗る。

追加だけでなく、削除や変更もできる。新しい番号のファイルに `ALTER` や `DROP` を書けばよい。残る課題は次のとおり。

- あるべき最終形が1か所に書かれていない。履歴の積み重ねから頭の中で組み立てる必要がある。
- 変更の SQL を毎回手で書く。SQLite は `ALTER TABLE` でできることが少なく（列の型の変更などができない）、「新しいテーブルを作ってデータを移し、古いのを消す」手順を手で書くことになる。
- アプリのコードと二重管理になる。Step 4 では、テーブルの定義（SQL）とは別に、コード側で `type Memo` を書き、SQL の文字列に `created_at AS createdAt` と書いて手で合わせた。列名を変えると、ずれは実行して初めて分かる。
- 誰かが本番に直接 DDL を流すと、記録と実物がずれる（drift）。気づく仕組みはない。

## 3. Drizzle

TypeScript の ORM。役割の違う2つのパッケージに分かれていて、構成管理とアプリのコードの両方に効く。どちらも `schema.ts` を唯一の正として使う。

### 構成管理の面：drizzle-kit（開発用）

1. `schema.ts` に、あるべきテーブルの形を書く（宣言的）。
2. `drizzle-kit generate` が、前回の形の記録（`migrations/meta/` のスナップショット）と比べて差分を出し、マイグレーションの SQL ファイルを作る。SQLite でのテーブルの作り直しのような面倒な手順も、自動で書いてくれる。
3. できた SQL は普通のマイグレーションなので、これまでどおり wrangler で流す。適用の記録や再現性といった、マイグレーションのよさはそのまま残る。

つまり「宣言的に書いて、手続き的に適用する」。あるべき姿は `schema.ts` を見れば分かり、変更の手順は自動で作られる。

注意点：

- 差分の比較相手は、実物の DB ではなくスナップショット。Terraform の `plan` のように実物を見に行くわけではないので、本番に直接 DDL を流した drift は検出できない。
- 自動で作られた SQL も、流す前に読む。たとえば列名を変えたとき、「名前の変更」なのか「削除して追加」（データが消える）なのかを、drizzle-kit が対話的に聞いてくる。

### アプリのコードの面：drizzle-orm（デプロイされる本体）

- クエリを、`schema.ts` で定義したオブジェクトを使って TypeScript で書く（`db.select().from(memos)` など）。
- 結果の型が定義から自動で決まるので、`type Memo` を手で書かなくてよい。`created_at` → `createdAt` の対応も定義で1回書けば済む。
- 列名を変えると、その列を使っているコードがすべてエディタで赤くなる。ずれが実行前に分かる。
- 値は自動でプレースホルダーに入るので、SQL インジェクションの心配が減る。
- 書き方は SQL に近い（`select`、`where`、`orderBy`）。Hibernate のような「SQL を隠す」重い ORM とは違い、どんな SQL になるかが想像しやすい薄い ORM。

### 隠れるもの

- 実際に流れる SQL が、コードからは直接見えなくなる。性能の問題を調べるときなどは、生成された SQL を確認する必要がある。
- `schema.ts` を手で書いた SQL と並べて混ぜると、Drizzle の記録と実物がずれる。Drizzle を入れたら、テーブルの変更は必ず `schema.ts` から行う。

## 途中から Drizzle を入れるときの問題（ベースライン）

Drizzle は自分のスナップショットと比べて差分を作る。手書きのマイグレーションだけがあって、スナップショットがない状態で最初に `generate` すると、「テーブルを作る」SQL がもう一度作られ、既存のテーブルとぶつかる。Flyway でいう「ベースライン」の問題。

対処は2通り。

- テストデータしかないなら、手書きのマイグレーションを捨て、DB を作り直して、Drizzle に最初から作らせる（このロードマップのやり方）。
- 本番データがあるなら、最初に作られた SQL を「適用済み」として扱う（適用の記録表に手で登録するなど）。
